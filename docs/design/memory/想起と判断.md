# 想起と判断

## この文書で定める範囲

この文書では、次を正本として定める。

- `RecallHint` の役割と最小契約
- 同期想起の基本フロー
- `RecallPack` の構成
- `episodes` と `events` の使い分け
- `episodes` の継続列の扱い
- `events` の例外参照の使い方

ユーザー発話、内部コンテキスト、検索用拡張クエリの分離方針は [../llm/プロンプト文脈分離方針.md](../llm/プロンプト文脈分離方針.md) を正とする。

## 基本前提

OtomeKairo では、会話と行動を別々の知能として扱わない。
両方とも、「入力を受け、記憶を踏まえて、何をするべきかを判断する」という同じ中心ループの分岐として扱う。

この前提により、次が成立する。

- 会話だけが現在の個の表現ではない
- 行動も、人格設定と記憶から組み上がる現在の個の文脈の延長で決まる
- 会話用の記憶と行動用の記憶を別系統に分けずに済む

ただし、同じなのは判断の土台までである。
判断後に求められる出力契約は、会話と行動で異なる。

## 共通本体

会話でも行動でも、共通本体は次の流れにする。

1. 現在入力を受け取る
2. `RecallHint` を作る
3. 構造レーンと連想レーンで必要な記憶を集める
4. `RecallPack` を作る
5. 判断系が結果種別を選ぶ
6. 分岐先ごとの処理を実行する
7. 結果を `events` に保存し、記憶更新へ返す

ここで重要なのは、会話と行動で最初から別の想起系を作らないことである。
同じ想起系で現在の個の文脈を作り、その後で分岐する。

## 共通本体で扱う入力

共通本体が受けるものは、厳密には「ユーザー入力」ではなく「現在入力」である。

主に入る入力は次である。

- 最新の対話入力
- 直近会話
- 定期思考や外界変化の事実
- 軽量なクライアント文脈
- 現在時刻

会話時は `最新入力` が主入力になり、自発判断時は `定期思考 + 軽量文脈` が主入力になる。

## `AnswerContract`

`AnswerContract` は直接根拠の種類だけでなく、根拠を検索する人物と会話の範囲を入力解釈LLMが選ぶ契約である。
`reason_codes` は想起前にこの検索契約を選んだ理由として audit と trace に保持する。検索後の判断・表現・根拠審査へ渡す圧縮契約からは外し、根拠の有無は取得後の `RecallPack / evidence_pack` で判断する。
`target_person_ref / target_interaction_ref` は構造化された参照IDを持ち、全人物または全会話を明示的に対象とするときだけ、それぞれ `null` にする。
本人との過去の会話を尋ねられた場合は、その人物を対象にする。特定の場を尋ねられた場合は会話の範囲も指定する。
同じ表示名でも参照IDで区別し、指定範囲に根拠が無い場合は欠落として扱う。別人物・別会話の根拠へ検索を広げない。
boundary、原文検索、特定したcycleの原文取得は同じ範囲を保持し、取得したeventの人物IDと会話IDを根拠・traceに残す。
`exact_boundary` はその範囲内の会話event全体の先頭・末尾を対象にする。活動など内容の条件を満たす最後の事実は `provenance` で該当する状態・記憶を根拠にする。
境界の日時は、検索が選定したeventの作成日時を生活文脈向けに整形して発話生成にも明示する。人物・会話の範囲とこの日時を回答の根拠にする。

## `RecallHint`

`RecallHint` は軽量高速 LLM が、現在入力と直近文脈だけを見て生成する入口情報である。
実装では `AnswerContract` と同じ `input_interpretation` 呼び出しで生成し、後段では `RecallHint` と `AnswerContract` を別々の契約として扱う。

入力は次に限定する。

- 現在入力
- `prompt_window` で取得した直近会話候補
- 生活文脈向けに整形した現在時刻
- ある場合だけの `visual_observation_context`
- ある場合だけの `activity_context`

`visual_observation_context` と `activity_context` は内部補助文脈であり、ユーザー発話ではない。
画像を指す入力の想起焦点を決める材料として使い、`current_input.text` へ連結しない。

直近会話候補は、選択中 `model_preset.prompt_window` の `recent_turn_minutes` と `recent_turn_limit` で取得する。
自己評価の外向き伝達判断用 `recent_interactions` は、同じ時間窓内に発話のある各場について、最新 `recent_turn_limit` 件までを時系列順に取得する。件数枠は場ごとに独立し、別の場の発話量で押し出さない。取得元は選択中記憶集合の `conversation_input / speech` event であり、新しい永続状態や LLM 要約は設けない。
この文脈の用途と role 境界は [../llm/プロンプト文脈分離方針.md](../llm/プロンプト文脈分離方針.md) を正とする。
`RecallHint` は取得済み候補から最大 6 発話だけを使う。
`RecallHint` 用の追加設定は持たない。
この段階では長期記憶を読まない。
現在時刻は `2026年4月25日 土曜日 9時00分（日本時間）` のような自然文で渡す。
LLM には UTC timestamp や offset 付き ISO timestamp を主要表現として渡さない。

`RecallHint` の最小契約は次とする。

- `primary_recall_focus`
- `secondary_recall_focuses`
- `confidence`
- `time_reference`
- `focus_scopes`
- `mentioned_entities`
- `mentioned_topics`
- `risk_flags`

`primary_recall_focus` は必ず 1 つにする。
`secondary_recall_focuses` は補助扱いとし、最大 2 件までに留める。
`focus_scopes`、`mentioned_entities`、`mentioned_topics` は、それぞれ最大 4 件までに留める。
`risk_flags` は主軸の危うさを表す補助扱いとし、最大 3 件までに留める。

`focus_scopes` の対象は次に留める。

- `self`
- `entity:<key>`
- `relationship:<key>`
- `topic:<key>`

第三者名や固有名は `focus_scopes` へ広げず、`mentioned_entities` で扱う。
`mentioned_entities` は `person:<normalized_name>`、`place:<normalized_name>`、`tool:<normalized_name>` の正規化済み参照を返す。
`mentioned_topics` は `topic:<normalized_name>` の正規化済み参照を返す。
`world` は `focus_scopes` へ入れない。
実装は未対応形式の `focus_scopes` を意味補完せず破棄する。
特定対象に閉じない世界理解は、`primary_recall_focus=fact` または `primary_recall_focus=state` で、現在入力が世界条件を主題にしている場合だけ構造レーンで扱う。

`primary_recall_focus` の enum は次で固定する。

- `self`
- `person`
- `relationship`
- `commitment`
- `topic`
- `preference`
- `fact`
- `state`
- `episodic`

`secondary_recall_focuses` も同じ enum を使う。

`time_reference` の enum は次で固定する。

- `none`
- `recent`
- `past`
- `future`
- `persistent`

`risk_flags` の enum は次で固定する。

- `mixed_intent`
- `ambiguous_reference`
- `weak_memory_cue`
- `time_ambiguous`

役割は次のとおりである。

- どの `scope` を優先するか
- どの `RecallPack` section を重くするか
- どの記憶焦点を主軸にするかを決める
- 時間軸を決める
- 主軸だけでは危うい点を `risk_flags` で後段へ渡す

ここで重要なのは、複合意図や曖昧参照をこの段階で解き切ったことにしないことである。
主軸は `primary_recall_focus` で持ち、危うさは `risk_flags` で持つ。

## 複合焦点の扱い

複合焦点を同時最適化しない。
`primary_recall_focus` を 1 本の主軸とし、`secondary_recall_focuses` は軽い補助としてだけ使う。

固定するのは次である。

- 想起と判断の主ルーティングは `primary_recall_focus` で決める
- `secondary_recall_focuses` は `primary_recall_focus` を上書きしない
- `risk_flags` は主ルーティングを上書きしない
- 1 判断サイクルで複数の主結果を同時に出さない

`secondary_recall_focuses` と `risk_flags` の効き先は次に限定する。

- 想起候補の rerank
- `RecallPack` の section boost
- `conflicts` の確認補助
- 返答方針や確認質問の補助

## `RecallHint` の validator

`RecallHint` の validator は、意味補正を行う層ではない。
軽量高速 LLM が返した出力が契約を満たしているかだけを確認する。
parser は validator 前に軽い正規化を行う。
`confidence` の引用符付き数値だけは数値へ戻し、`"0.72"` は `0.72` に正規化する。
`secondary_recall_focuses`、`focus_scopes`、`mentioned_entities`、`mentioned_topics`、`risk_flags` は、妥当な値だけを残して重複を落とし、件数上限までに切り詰める。
`secondary_recall_focuses` に `primary_recall_focus` と同じ値が来た場合も、その要素は落とす。
`"high"`、`"70%"`、空文字列、非有限値は正規化せず、validator で失敗させる。

validator が確認する項目は次とする。

- JSON として解釈できること
- 必須キーがすべて存在すること
- `primary_recall_focus` が固定 enum のいずれか 1 件であること
- `secondary_recall_focuses` が同じ enum を使うこと
- `confidence` が `0.0-1.0` の数値であること
- `time_reference` が固定 enum のいずれかであること
- `risk_flags` が固定 enum の配列であること
- `focus_scopes`、`mentioned_entities`、`mentioned_topics` が配列であること
- 正規化後の `focus_scopes` が `self`、`entity:<key>`、`relationship:<key>`、`topic:<key>` のいずれかであること
- `mentioned_entities` が `person:<normalized_name>`、`place:<normalized_name>`、`tool:<normalized_name>` のいずれかであること
- `mentioned_topics` が `topic:<normalized_name>` であること
- 余計なトップレベルキーを持たないこと

ここでは、コード側で意味を補正しない。
mode や focus の置き換え、scope の推測補完、曖昧値の自動修正は行わない。
未対応形式の `focus_scopes` は推測補完せず破棄する。

一方で、想起全体の設計方針としては、意味的な候補選別や要約表現では LLM を第一候補とする。
ただし、件数上限、契約検証、状態遷移、失敗監査はコード側へ残す。
repo 全体の原則は [../llm/LLM判断優先方針.md](../llm/LLM判断優先方針.md) を正とする。

## `RecallHint` の再試行と失敗時の扱い

`input_interpretation` の再試行は 1 回までに限定する。
再試行するのは validator を通過しなかったときだけである。

2 回連続で validator を通らなかった場合、その判断サイクルはそこで打ち切る。
失敗後に、代替の想起や自然文フォールバックを作らない。

ログとしては、少なくとも次を残す。

- `events`
  - `recall_hint_failure` 相当の失敗イベント
- `retrieval_runs`
  - `result_status=failed`
  - `failure_reason`

## 同期想起の基本フロー

同期想起は、次の 2 レーンで行う。

1. 構造レーン
2. 連想レーン

構造レーンでは、`scope`、`memory_type`、`status` を軸に厳密候補を取る。
会話中の人物の episode 候補は、その人物の `entity` と `self|person_ref` の `relationship` の双方を基底に含める。主焦点が preference などの場合も、本人が過去に述べた経験や心情を関係 scope に保存していることだけで候補から外さない。関係モデルの主ルーティングは主焦点に従い、episode の人物境界とは分ける。
連想レーンでは、現在入力をクエリ化して `memory_units` と `episodes` をベクトル検索し、曖昧な連想を補助する。

ここでの原則は次である。

- 骨格は構造レーンで作る
- 主ルーティングは `primary_recall_focus` で決める
- `mentioned_entities` は `scope_type=entity` の構造候補取得に使う
- `mentioned_topics` は `scope_type=topic` の構造候補取得に使う
- `world` 候補は `scope_type=world` かつ `scope_key=world` に限定し、広域の世界知識探索には使わない
- `secondary_recall_focuses` は rerank と section boost に留める
- `risk_flags` は断定しすぎないための補助信号としてだけ使う
- 連想レーンは補助に留める
- 連想レーンの index 対象は `memory_units` と `episodes` に限定する
- `commitment` と `relationship` は構造レーン優先にする
- `vector-only` の候補は断定根拠にしない

### 固有対象の正規化と関係補強

`RecallHint` は長期記憶を読まない。
`entity_registry` による別名解決は、`RecallHint` の validator 通過後、構造レーンの候補取得前に行う。
この処理は `mentioned_entities` の正規参照を補正するだけで、`primary_recall_focus`、`secondary_recall_focuses`、`risk_flags` を変更しない。

`mentioned_entities` の扱いは次で固定する。

- `mentioned_entities` が既存 alias に一致した場合、対応する canonical `entity_ref` を構造レーンの `scope_filter` に使う
- `mentioned_entities` が既存 alias に一致しない場合、LLM が返した型付き参照をそのまま候補に使う
- 複数の canonical 候補に一致した場合、`risk_flags` の曖昧さを後段へ残し、単一対象へ確定しない
- alias 解決の結果は `retrieval_runs.payload_json.entity_resolution` と cycle trace の `recall_trace.entity_resolution` に残す

`relation_index` は、正規化済み entity から関係候補を補強するために使う。
`relation_index` は独立 section を作らない。
`relation_index` が返した根拠 `memory_unit_id` は、その記憶本来の `self_model / person_model / relationship_model / active_topics / active_commitments` の候補として扱う。
`active_commitments` へ入れる根拠は active な `commitment_state` を持つものに限定する。

`relation_index` の探索は 1-hop に限定する。
1-hop で見つかった隣接 entity をさらに展開しない。
関係候補は最大 12 件とする。
edge は `active`、`weak` の順に並べ、同じ状態では `salience`、`confidence`、`last_evidence_at` の降順にする。
関係候補の採用には、根拠になる `memory_units` の active な支持を必要とする。
`derived_status=inactive` の edge は通常想起候補に入れない。
`derived_status=weak` の edge は、確認寄りの判断材料として扱う。
読み取りは最後に transaction 完了した索引だけを対象とする。
読み取り時に支持元 `memory_unit` の現在の `status / valid_to` を再確認し、active な支持元がない edge を除外する。
再確認により active な `confirmed` 支持元がなくなった edge は、その想起では `weak` として扱う。
索引が空または更新失敗中でも全件検索へ切り替えない。
relation index 候補は既存の `recall_pack_selection` 呼び出しへ渡し、選別用の LLM 呼び出しを追加しない。

## `RecallPack`

`RecallPack` の主 section は、会話でも行動でも共通とする。

- `self_model`
- `person_model`
- `relationship_model`
- `active_topics`
- `active_commitments`
- `episodic_evidence`
- `conflicts`

この構成を分けない理由は、会話でも行動でも「その回の現在の個の文脈」を支える材料が同じだからである。

`RecallPack` の組み立てでは、次を守る。

- 候補収集時は section ごとの仮上限を持つ
- 最終 `RecallPack` は全体 40 件までに収める
- section 上限は `self_model` 4、`person_model` 8、`relationship_model` 8、`active_topics` 4、`active_commitments` 8、`episodic_evidence` 6、`conflicts` 4 とする
- `episodic_evidence` は短い要点に圧縮する
- `active_commitments` には `status in (inferred, confirmed)` かつ active な `commitment_state` のものだけを入れる
- `conflicts` は別枠で渡す

`RecallPack` 候補の意味的選別、section 配置、`conflicts` 文面を LLM で行うときの
role、入力契約、failure の扱いは
[RecallPackのLLM選別.md](RecallPackのLLM選別.md) を正とする。

### 現在の理解と過去の報告

出所を確認する `evidence_pack.speech_guidance` は、正確な原文・日時・出典の根拠を `evidence_items` に限る。現在または最後に把握した状態への回答では、本人発話、人物参照付き `ActivityContext`、観測、有効な継続理解も、それぞれの種類と時点を保った独立した根拠として使う。出所の証拠項目に入っていないことだけで、保持済みの活動や観測を未知にしない。
`exact_boundary` で根拠を特定したときは、選択した event の `created_at` を `evidence_pack.boundary_at` として渡す。これはその会話の発生日時であり、`event.text` や episode 要約で言及された別の出来事の日時と区別する。判断・表現・送信前審査はこの境界日時を共通の根拠にする。この契約のモデル入力では `episodic_evidence / event_evidence` の補助要約を外し、resolver が選んだ raw event を日時根拠にする。trace には候補と選択の記録を保持する。
`provenance` のモデル入力へ圧縮する際は、`ActivityContext.current_activity / last_known_activity` も `type=activity_context / source_kind=activity_state / evidence_kind=inference` の項目として根拠一覧に載せる。`context_kind` で現在有効な推定と最後の把握記録を分け、`actor_ref`、根拠からの経過ラベル、元の説明を保持する。過去の本人発話の逐語証拠とは種類を分ける。活動文脈の意味境界は [../runtime/activity_state.md](../runtime/activity_state.md) を参照する。

候補選別、判断、表現、送信前審査へ渡す圧縮表現でも、`memory_units` の `status / formed_at / last_confirmed_at / valid_from / valid_to` と `episodes.formed_at` を保持する。現在の人物の好みや継続理解は、最新の本人発話と、有効状態・期間を持つ継続理解から判断する。`episode` は当時交わされた報告や判断の記録であり、その後の訂正や変化を取り消す根拠にはしない。`summary` は根拠から再構成した理解として扱い、具体的な confirmed の理解と異なる場合は、人物・対象・時点・訂正の経緯を LLM で照合する。

有効な継続理解が選ばれているときは、それをその人物について今覚えている内容として答え、訂正履歴を確認できた範囲は別に説明する。訂正や変化が反映されたかを尋ねる質問と、新しい内容を伝える訂正の申告を LLM で区別する。確認質問は残る不明点のために使い、その質問が前提に置く出来事も同じ根拠へ照合する。起きたか未確認の出来事は、その有無から確認する。この境界を判断、表現、発話の根拠審査で共有する。

人物が当時述べた経験や心情は本人報告を根拠にする。過去の assistant の回答やその要約に未知とある場合も、本人の報告と照合する。現在の想起で確認できないことは未確認として伝え、経験や報告がなかったこととは区別する。

関連要約には `related_memory_type / related_status` と `related_claim`、`memory_link_context` の代表関係には `source_status / target_status` と `source_claim / target_claim` を残す。選定記憶とこれらの主張は共通に、種類、scope、`subject_ref / predicate / object_ref_or_value`、要約、status、形成・確認日時、有効期間、約束の状態と出所・更新の qualifiers を保持する。記憶の内部 ID は圧縮主張へ渡さず、人物・会話の参照は出所として保つ。status は、その記憶が表す理解や約束の有効性へ適用する。`memory_type / subject_ref / predicate` と更新の根拠を LLM で照合し、`revoked` は取り消した理解、`superseded` は後の理解への置換履歴として、更新された主張とその期間を判断する。置換前の要約に含まれる対象名や本人報告は、更新された主張と分けて根拠へ照合する。共有条件や方針だけが変更された場合、情報を知った経験と未変更の内容の根拠を保持し、現在の共有条件で伝えられる範囲を決める。情報の根拠を確認できることと、現在の相手へ開示できることを区別し、共有を留保する回答では未確定の許可条件を説明する。この意味境界を判断、表現、発話の根拠審査で共有する。

### 共有許可と受け手の照合

共有許可は、情報の本人、許可された受け手、共有内容、共有先、有効条件を対応させて扱う。現在の応答相手の同定と、その相手が本人の許可した受け手であることの照合は別である。本人とは別人であることや、同じ呼び名の別人が文脈にいることだけでは、許可先との同一性は確定しない。

本人、別人、その人などの相対的な人物表現は、元の報告の話者と参加者に対応させて解釈する。過去の報告で本人とは別人とされた受け手を、現在の応答相手とは別人へ読み替えない。証拠要約の出所は [event_evidenceのLLM圧縮.md](event_evidenceのLLM圧縮.md)、候補の主張投影は [RecallPackのLLM選別.md](RecallPackのLLM選別.md) の契約を参照する。

許可先が未同定なら、記憶解釈と要約でも許可条件と未同定であることを保ち、共有を保留する理由と本人による受け手の特定が必要であることを現在の応答相手へ伝える。本人への確認を実行する場合は、[判断と行動の連絡手段の境界](../runtime/判断と行動.md#人物への連絡手段)に従って、利用できる能力と宛先を確かめる。許可先を応答相手の `person_ref` に対応させる根拠が得られたとき、その内容と共有先の範囲で開示できる。継続的な共有範囲の指示の有効期間は、本人による変更や期限に沿って扱い、一度の会話中の指示とは区別する。この意味境界を人物参照、記憶解釈、要約、判断、表現、`disclosure_review` で共有する。

本人の後の説明が未同定の条件を満たしたときは、同じ許可の受け手が確定した更新として扱う。記憶更新では対応する未確認の理解を置き換え、確認の約束を履行済みとして整理し、詳細と公開先の制限は保持する。想起と判断では根拠の人物、範囲、時点を照合し、解消済みの未確認の履歴と現在も未解決の競合を区別する。

`disclosure_review` には、採用済みの判断と、その判断・発話の根拠審査が参照した同じ選定済み `RecallPack` を渡す。モデルへの投影でも、現在の相手、許可の本人と受け手、主張の範囲・期間、更新元の本人報告を保ち、解消済みの条件を現在の未確認条件へ戻さずに開示範囲を照合する。

### `memory_links` の想起利用

`memory_links` は独立 section にしない。
`memory_units` の周辺関係を説明する補助情報として `RecallPack` に載せる。

扱いは次で固定する。

- 候補選別前に candidate `memory_units` の周辺 `memory_links` を読み、各候補へ `memory_link_summary` を付ける
- `memory_link_summary` は `label_counts` と少数の `representative_links` だけを持つ
- `memory_link_summary` の label は `supports / contradicts / derived_from / about_same_scope / affects` をそのまま使う
- `recall_pack_selection` role へ渡す候補には、永続 ID ではなく短い関係要約だけを含める
- 選定後に `selected_memory_ids` の周辺 `memory_links` を読み直し、`RecallPack.memory_link_context` に `link_count`、`label_counts`、`representative_links` を持たせる
- 読み込み済みの `derived_from` のうち、選定記憶から直接参照する `superseded / revoked` の更新元について、根拠 event を合計 16 件まで読み、person の発話を `source_reports` に載せる。本文全体、話者、参加者、会話参照、発生日時を保持し、内部 event ID はモデル入力へ渡さない
- 判断モデルへ渡す `memory_link_context` は内部 ID を除いた compact 表現にする
- inspection と `retrieval_runs` には `memory_link_context` と `recall_pack_selection.memory_link_*` を残す

`memory_links` は、選ばれた記憶の関係を説明するために使う。
`memory_links` の先にある未選定 `memory_unit` を、この段階で `RecallPack` 本体へ昇格しない。
候補外の graph traversal は行わない。

`source_reports` は、選定記憶の更新を理解するための直接の出所である。通常の `event_evidence` を取得しない想起でも同じ範囲で取得し、別の会話や人物の探索は広げない。読み込み対象の根拠 event が欠けた場合は明示的に失敗する。置換された記憶の status は主張の有効性へ適用し、本人が当時述べた情報と現在の条件の関係は、本文・出所・時点に基づいて LLM が判断する。

`memory_type=summary` は、独立 section を作らず既存 section に混ぜる。
対応は次で固定する。

- `scope_type=self`
  - `self_model`
- `scope_type=entity`
  - `person_model`
- `scope_type=relationship`
  - `relationship_model`
- `scope_type=topic`
  - `active_topics`

`scope_type=entity` と `scope_type=world` も独立 section を作らない。
対応は次で固定する。

- `scope_type=entity`
  - その対象自体の継続理解は `active_topics`
  - その対象を含む出来事の根拠は `episodic_evidence`
  - `self` と人物との関係理解は `relationship_model`
- `scope_type=world`
  - 現在入力の事実確認や状態判断に効くものだけ `active_topics`
  - 出来事根拠が主であるものは `episodic_evidence`

## `episodes` と `events` の使い方

想起の標準経路は、`memory_units + episodes` とする。

- `memory_units`
  - 継続理解の主軸
- `episodes`
  - 経験のまとまりと回想の主軸

`events` は標準経路には入れない。
ただし、次のときだけ例外的に使う。

- そのとき何を話したかを確認したい
- その場で何を決めたかを確認したい
- 実行の由来を短く確かめたい

このときも、`events` 全文を広く再読しない。
選定件数、precise 追加、LLM 圧縮の上限と失敗境界は [event_evidenceのLLM圧縮.md](event_evidenceのLLM圧縮.md) を正とする。

## 正確引用と詳細時系列を標準責務にしない

想起系の標準責務に、正確引用や詳細時系列の再構成を含めない。

## 検索用拡張クエリ

recall、embedding、evidence resolution は、会話添付画像や視覚観測の詳細な視覚説明から作った `augmented_query_text` を検索・根拠抽出に使う。
後から視覚確認が必要な場合は、短い memory だけでなく `visual_observation_record.detailed_summary_text` を根拠候補にする。
検索一致した視覚記録と直近の視覚記録は、判断と応答へ渡すために `RecallPack.visual_observations` へ入れる。
日単位、反復、傾向の確認が必要な場合は、`daily_visual_digest` を `RecallPack.visual_daily_digests` へ入れる。
`augmented_query_text` は内部派生値であり、ユーザー発話の原文ではない。
trace と source pack では `input_text` ではなく `augmented_query_text` として表示する。
内部要約を `augmented_query_text` へ追加する場合は、`<<<OTOMEKAIRO_INTERNAL_CONTEXT ...>>>` と `<<<END_OTOMEKAIRO_INTERNAL_CONTEXT>>>` で囲む。
`[要約]` のような短い区切りは使わない。
会話判断、発話、記憶化に渡す `input_text` はユーザー原文だけを指す。

## `visual_observations` の想起投入

`visual_observation_record` は、画像内の物体、場所、画面要素、背景要素の有無確認に使う正本である。
`daily_visual_digest` と `memory_unit` は、特定画像内の対象有無を直接断定する正本ではない。

`RecallPack.visual_observations` は最大 8 件に制限する。
選定では次の枠を持つ。

1. 検索一致枠: query text が `detailed_summary_text / scene_entities / searchable_terms` に強く一致する記録
2. 重要枠: 会話結合、ユーザー関心、`importance_score` が高い記録
3. 直近枠: 現在判断に近い新しい記録

特定対象の有無確認では、検索一致枠を最優先する。
`retention_status=compressed` でも query に強く一致する記録は、query に弱く一致する `active` より上に置く。
日次整理前の当日記録は大量に `active` のまま残るため、直近枠だけで `RecallPack.visual_observations` を埋めない。
同一 duplicate group または同一 source の連続記録は代表を優先し、似た記録で投入枠を埋めない。

`excluded` は通常想起へ投入しない。
`compressed` は通常想起の優先度を下げるが、検索対象から外さない。

## `visual_daily_digests` の想起投入

`visual_daily_digests` は、`visual_observation_records` の詳細説明を置き換えない。
`visual_daily_digests` は、日単位の経験、反復した活動、環境、作業対象を短く確認するための補助 section とする。

`RecallPack.visual_daily_digests` の item は次を持つ。

- `digest_id`
- `local_date`
- `record_count`
- `group_count`
- `retained_count`
- `compressed_count`
- `group_summaries`
- `memory_candidate_summaries`

`group_summaries` は最大 8 件に制限し、各 item は `summary_text / record_count / first_observed_at / last_observed_at / representative_visual_observation_id` だけを判断へ渡す。
`memory_candidate_summaries` は最大 8 件に制限し、長期記憶として確定した事実ではなく、日次整理が作った候補として扱う。

取得順は次とする。

1. 日付参照がある入力では該当日の digest を優先する
2. 日付参照が無い入力では、検索語に一致する digest を優先する
3. 検索語に一致しない場合は直近の digest を最大 4 件だけ入れる

`visual_observations` と `visual_daily_digests` の両方が入る場合、特定の対象有無は `visual_observations[].detailed_summary_text` を優先する。
`visual_daily_digests` だけで答える場合は、日次整理の要約に基づく回答として不確実性を残す。

ここで優先するのは次である。

- 何が話題だったか
- 何が決まったか
- 何が継続しているか
- いまの判断に何が効くか

そのため、通常想起では `memory_units` と `episodes` を主に使い、必要時だけ `events` を狭く証拠参照する。

## `episodes` の継続列の扱い

通常想起では、まず `episode` 単体を選ぶ。
継続性が必要な場合だけ、選ばれた `episodes` の `episode_series_id` を使って近接する `episodes` を追加で見る。

継続列をたどるのは、次のような場合に限る。

- `open_loops` の続きや確認待ちが現在の判断に効く
- 約束確認や進行中タスクの途中経過を見たい
- 後から返った実行結果の由来を短く確かめたい

単に同じ話題が続いているだけなら、継続列を標準経路にしない。

継続列をたどる場合も、同じ `episode_series_id` を持つ `episodes` 全件を広く並べない。
現在の判断に近いものを最大 1-2 件だけ追加し、通常の `RecallPack` に混ぜて使う。

## `event_evidence` の圧縮ルール

`event_evidence` は、`events` の永続表現ではない。
細部確認が必要になったときだけ、その回の想起の中で一時的に作る短い証拠表現として扱う。

形式は、次のスロット型とする。

- `anchor`
  - 場所、時期、出来事名などの短いアンカー
- `topic`
  - その `event` で主に話題になっていたこと
- `decision_or_result`
  - その場で決まったこと、確認されたこと、実行結果
- `tone_or_note`
  - 雰囲気や補足。ただし断定に効く主根拠にはしない

各スロットは簡潔に留める。
空欄は省略する。

圧縮時は、次を守る。

- 生ログの言い回しを長くそのまま再掲しない
- 断片をつなげて新しい事実を捏造しない
- 雑音になりやすい相槌や言い直しは落とす
- 判断に効くなら `decision_or_result` を優先し、回想に効くなら `anchor` と `topic` を残す

`event_evidence` の圧縮を LLM で行うときの role、入力契約、failure の閉じ込め方は
[event_evidenceのLLM圧縮.md](event_evidenceのLLM圧縮.md) を正とする。

## 直近窓の外にある曖昧参照は限定対応にする

直近窓の外にある曖昧参照を全面的には解かない。
ここでは、限定対応だけを責務に含める。

基本方針は次である。

- まず構造レーンで `active_topics`、`active_commitments`、関係、嗜好の候補を絞る
- 次に `memory_units` と `episodes` の通常想起で近い候補を取る
- 候補が狭まった場合だけ、関連 `event_id` を開いて短い `event_evidence` を作る
- その圧縮根拠だけでは危ういときだけ、selected source に残る sibling `event_id` を追加で開く
- それでも断定できない場合は、確認寄りに倒す
- 件数上限は [event_evidenceのLLM圧縮.md](event_evidenceのLLM圧縮.md) を正とする

限定ロードを行ったかどうか、追加件数、判定理由は `recall_trace.event_evidence_generation` と audit event から追えるようにする。

## 想起系が作る内部コンテキスト

想起系は、判断コンテキストのうち記憶文脈部分を作る。
判断モデルへ渡す統合コンテキスト全体の正本は [../runtime/判断と行動.md](../runtime/判断と行動.md) を正とする。

想起系から判断モデルや返答モデルへ渡すものは、次の 2 つに分ける。

- 直近会話
- 内部コンテキスト

想起系が作る内部コンテキストの最小形は次である。

- `TimeContext`
- `AffectContext`
- `RecallPack`

ここで重要なのは、生ログ全文をそのまま並べないことである。
会話の流れは直近会話で持ち、長期記憶は役割別に圧縮して渡す。
`world_state`、`runtime_state`、`capability_state`、`drive_state`、`ongoing_action`、保留意図、`initiative_context` は統合判断コンテキスト側で扱う。

## `TimeContext`

現在の生活時刻、曜日、時間帯を持つ。生活時刻の自然文は秒を保持し、指定時刻や実行機会と同じ精度で照合できるようにする。分単位の表示で期限未到達へ読み替えない。判断、発話、送信前確認、作業完了審査はこの共通の時刻表現を使う。

## `AffectContext`

`AffectContext` は、`mood_state`、関連 `affect_state`、必要時だけ直近 `episode_affect` を判断用に圧縮した内部コンテキストである。

少なくとも次を守る。

- 全 `episode_affect` と全 `affect_state` をそのまま渡さない
- `mood_state` は常に含める
- `mood_state` は数値状態だけを持ち、自然文は持たない
- `affect_state` は現在入力と `RecallHint` に関係する `target_scope` だけを見る
- 直近 `episode_affect` は原因追跡や当時感情の参照が必要な場合だけ少数を渡す
- `self` の機嫌と主要な `relationship` を優先する

ここで重要なのは、感情を単独で判断させないことである。
`AffectContext` は `RecallPack` を補う前景情報であり、記憶や現在入力の代替ではない。

## 想起後の判断との境界

想起が作るのは現在の個の文脈までである。
その文脈を見て何を返すか、行動するか、保留するか、何もしないかを決める責務は [../runtime/判断と行動.md](../runtime/判断と行動.md) に置く。

この分離により、想起系は「何を思い出すか」を扱い、行動系は「何を選ぶか」を扱う。
