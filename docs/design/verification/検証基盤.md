# 検証基盤

## 目的

この文書は、OtomeKairo の検証手順と検証層の正本である。
通常作業では短時間で回る検証を標準にし、時間がかかる検証は必要時の手動確認に分ける。

## 検証層

| 層 | 目的 | 標準コマンド | 位置づけ |
| --- | --- | --- | --- |
| fast test | 契約、validation、境界処理を決定的に確認する | `.venv/bin/python -m pytest tests` | 通常作業で毎回実行する |
| mock smoke | mock LLM でサーバ全体の代表フローを確認する | `.venv/bin/python scripts/run_long_smoke.py --profile smoke` | 大きな変更前後に手動で実行する |
| real LLM smoke | 実 LLM の判断構造と trace shape を確認する | `.venv/bin/python scripts/run_long_smoke.py --profile real-llm-smoke --keep-artifacts` | 実 LLM 設定がある環境で必要時に実行する |

## 通常検証

通常検証は fast test だけにする。
目標実行時間は 1 分以内とする。

```bash
.venv/bin/python -m pytest tests
```

fast test には、LLM 呼び出し、サーバ常駐起動、長時間待機、外部サービス接続を入れない。
fast test は、仕様が固まっている機械的な境界を確認する。

対象は次である。

- config validation
- LLM structured output の契約検証
- capability schema validation
- event stream hello / capability binding
- 文字列ぶつ切り禁止
- 秘密情報を保存、ログ、inspection へ出さない境界

## 重い検証

mock smoke と real LLM smoke は通常検証へ入れない。
これらはサーバ起動、scheduler、memory worker、capability result follow-up、inspection trace を含むため、実行時間が長い。

mock smoke は、次の代表フローをまとめて確認する。

- 通常会話
- 定期思考
- capability request / result follow-up
- memory worker
- vision capture
- 記憶と想起の代表ケース

real LLM smoke は自然文の完全一致を検証しない。
合否は `summary.json` の verified flag と trace shape で判定する。
API key、token、camera account は artifact、ログ、サンプルへ出さない。

### 実会話と仮想時間

`scripts/run_virtual_time_conversation.py` は、専用プロセスと新しい記憶DBで実LLM会話と生活時刻の前進を組み合わせる手動検証である。人格、主モデル、送信前チェック、embedding、活動トピックは現在設定を引き継ぎ、通常環境の記憶へ検証発話を入れない。

```bash
PYTHONPATH=src .venv/bin/python scripts/run_virtual_time_conversation.py \
  --capture-camera --artifact-dir tmp/virtual-time-conversation
```

生活時刻の取得元をアプリ読み込み前に差し替え、保存、会話窓、想起、感情、予定、日次整理で同じoffset付き日本時間を使う。後から設置して読み込み済みの時刻取得元を残す起動は明示的に失敗させる。OS時刻、通信timeout、応答時間計測は実時間のままとする。仮想時計は巻き戻さず、期限直前・到来・経過を独立に確認する。細かな前進でも登録済みの将来予定を走査し、越える期限を先に確認する。時刻の意味は [../runtime/時刻モデル.md](../runtime/時刻モデル.md) を参照する。

30日後までの代表時刻で3人・90ターン以上の会話と30回以上の無言期間の自律判断を行う。全定期起床を再現する負荷試験ではない。HTTPとWebSocketの配送、状態の失効、感情の減衰、翌日と翌週の予定、停止、会話との競合、再起動を照合する。実画像は仮想外界の入力として再生し、物理カメラで未来の撮影を行ったとは扱わない。音声品質と応答速度の改善はこの検証の対象外である。

自然文の意味評価には主モデルの実LLM補助を使い、本人発話、時刻、内部trace、実際の状態を照合する。同名人物も人物ID・会話IDで分け、採用されたtraceも検証対象にする。送信前チェックのモデル設定は実環境のものを引き継ぐ。語句の一致で合否を決めない。`summary.json.verified` は必要件数と機械的境界の通過に加え、意味評価にfailやinconclusiveが残っていない場合だけtrueとする。`--mock` は時計と配送の機械的確認だけを行い、実会話の成功とは扱わない。

検証用DB、複製設定、証明書、画像、詳細ログは一時ディレクトリへ置き、通常終了時に削除する。`--keep-private` は原因調査に必要な場合だけ使い、調査と再検証の終了後に明示的に削除する。保存する結果から認証値を除き、会話、仮想時刻履歴、意味評価、状態の証拠、実時間の応答時間を残す。

各会話の直前に専用DBをsnapshotとして保存し、意味評価が通過したものは削除する。failやinconclusiveが残ったsnapshotは原因調査と同じ時刻での再検証に使う。`--cases-file` は `case_id / person / text / expected / cancel_all / virtual_time` を持つcase配列を受ける。開始時刻は最初のcaseのvirtual_timeとする。`--seed-data-dir` はそのcase直前の検証用snapshotディレクトリを指定する。画像sourceの有効状態もsnapshotと照合し、有効だったcaseには保存した `observation.jpg` を `--vision-image` で指定する。通常DBを再検証のseedに指定することは受理しない。再検証の `summary.json.profile=replay` は指定caseの結果であり、30日間の検証結果とは別に扱う。

## 代表ケースの割り当て

設計済みの代表ケースは、次の基準で検証層へ割り当てる。

- 入出力が決定的で、LLM やサーバ起動が不要なものは fast test に置く
- 判断サイクル、scheduler、memory worker、event stream をまたぐものは mock smoke に置く
- 実 LLM の判断構造を確認するものは real LLM smoke に置く

自律判断 matrix、capability result follow-up、記憶品質、視覚観測は、当面 `scripts/run_long_smoke.py` を正とする。
fast test へ移すのは、仕様が固まった deterministic な境界に限定する。

## 合否基準

fast test は pytest の exit code を合否にする。
mock smoke と real LLM smoke は exit code と `summary.json` の verified flag を合否にする。
LLM の自然文表現、完全な出力文面、偶発的な語彙選択を合否にしない。
