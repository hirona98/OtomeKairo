# 検証基盤

## 目的

この文書は、OtomeKairo の検証手順と検証層の正本である。
通常作業では短時間で回る検証を標準にし、時間がかかる検証は必要時の手動確認に分ける。

## 検証層

| 層 | 目的 | 標準コマンド | 位置づけ |
| --- | --- | --- | --- |
| fast test | 契約、validation、境界処理を決定的に確認する | `.venv/bin/python -m pytest tests` | 通常作業で毎回実行する |
| mock smoke | mock LLM でサーバ全体の代表フローを確認する | `.venv/bin/python scripts/run_long_smoke.py --profile smoke` | 大きな変更前後に手動で実行する |
| real LLM smoke | 実 LLM の判断構造と trace shape を確認する | `.venv/bin/python scripts/run_long_smoke.py --profile real-llm-smoke --keep-artifacts` | 実 LLM 設定がある環境で必要時に実行する |

## 通常検証

通常検証は fast test だけにする。
目標実行時間は 1 分以内とする。

```bash
.venv/bin/python -m pytest tests
```

fast test には、LLM 呼び出し、サーバ常駐起動、長時間待機、外部サービス接続を入れない。
fast test は、仕様が固まっている機械的な境界を確認する。

対象は次である。

- config validation
- LLM structured output の契約検証
- capability schema validation
- event stream hello / capability binding
- 文字列ぶつ切り禁止
- 秘密情報を保存、ログ、inspection へ出さない境界

## 重い検証

mock smoke と real LLM smoke は通常検証へ入れない。
これらはサーバ起動、scheduler、memory worker、capability result follow-up、inspection trace を含むため、実行時間が長い。

mock smoke は、次の代表フローをまとめて確認する。

- 通常会話
- 定期思考
- capability request / result follow-up
- memory worker
- vision capture
- 記憶と想起の代表ケース

real LLM smoke は自然文の完全一致を検証しない。
合否は `summary.json` の verified flag と trace shape で判定する。
API key、token、camera account は artifact、ログ、サンプルへ出さない。

### 実会話と仮想時間

`scripts/run_virtual_time_conversation.py` は、専用プロセスと新しい記憶DBで実LLM会話と生活時刻の前進を組み合わせる手動検証である。人格、主モデル、送信前チェック、embedding、活動トピックは現在設定を引き継ぎ、通常環境の記憶へ検証発話を入れない。

```bash
PYTHONPATH=src .venv/bin/python scripts/run_virtual_time_conversation.py \
  --capture-camera --artifact-dir tmp/virtual-time-conversation
```

生活時刻の取得元をアプリ読み込み前に差し替え、保存、会話窓、想起、感情、予定、日次整理で同じoffset付き日本時間を使う。後から設置して読み込み済みの時刻取得元を残す起動は明示的に失敗させる。OS時刻、通信timeout、応答時間計測は実時間のままとする。仮想時計は巻き戻さず、期限直前・到来・経過を独立に確認する。細かな前進でも登録済みの将来予定を走査し、越える期限を先に確認する。時刻の意味は [../runtime/時刻モデル.md](../runtime/時刻モデル.md) を参照する。

将来の働きかけの開始審査にも同じ生活時刻が渡ることを確認し、候補の具体的な日時と相対時間がその基準に合う場合と、過去・別時刻の場合を実LLMで区別する。開始前の拒否は、時刻・候補・審査理由を記録したeventで追う。開始審査と監査記録の契約は [../runtime/autonomous_run.md](../runtime/autonomous_run.md#開始前意味検証) と [../runtime/デバッグ可能性.md](../runtime/デバッグ可能性.md#decision_trace) を参照する。

判断生成中に生活時刻を進める再生も行い、相対時刻の予定が入力サイクルの起点を保つことを確認する。実LLMの記録済み判断を固定する場合は、その節点が再生データであることと、後続の審査・step・発話で実APIを使った範囲を成果物へ明記する。起点時刻と保存時刻の意味は [../runtime/autonomous_run.md](../runtime/autonomous_run.md#完了前意味検証) を参照する。

30日後までの代表時刻で3人・90ターン以上の会話と30回以上の無言期間の自律判断を行う。全定期起床を再現する負荷試験ではない。HTTPとWebSocketの配送、状態の失効、感情の減衰、翌日と翌週の予定、停止、会話との競合、再起動を照合する。実画像は仮想外界の入力として再生し、物理カメラで未来の撮影を行ったとは扱わない。音声品質と応答速度の改善はこの検証の対象外である。

自然文の意味評価には主モデルの実LLM補助を使い、本人発話、時刻、内部trace、実際の状態を照合する。同名人物も人物ID・会話IDで分け、採用されたtraceも検証対象にする。送信前チェックのモデル設定は実環境のものを引き継ぐ。語句の一致で合否を決めない。`summary.json.verified` は必要件数と機械的境界の通過に加え、意味評価にfailやinconclusiveが残っていない場合だけtrueとする。`--mock` は時計と配送の機械的確認だけを行い、実会話の成功とは扱わない。

能力要求を選んだ会話・定期思考は、要求IDと保存済みの後続traceで非同期の結果chainを追跡してから評価する。後続判断がさらに能力を要求した場合は、その判断の `followup_result_summary.followup_capability_request_summary` に保存された次の要求IDを追う。最初のHTTP応答と、後続の判断・実際に配送された返答を別に保存する。後続発話は要求ID、判断cycle、本文、会話ID、宛先人物を照合する。本文は正本の `events` に保存された一意の発話全文を用いる。監査表示用の `speech_summary` は全文照合の対象にしない。重複した判断・配送や循環した要求は明示的に失敗させる。最初の能力要求に発話がないことだけで無回答とせず、最終結果と後続判断が採用した根拠もLLMへ渡す。能力結果と外向き応答先の意味は [../runtime/判断と行動.md](../runtime/判断と行動.md) を参照する。

能力要求に `autonomous_run_id` がある場合は、自律作業の正式な結果経路として扱う。途中の能力結果から自律作業へ移った場合も同じ経路を追跡する。要求要約の参照を保持する責務は [../runtime/デバッグ可能性.md](../runtime/デバッグ可能性.md) を正とする。要求に指定された作業IDの起点cycle・会話・宛先を照合し、進行中の判断と結果待ちが終わるまで待つ。予定待ち・保留・終端は、それぞれ保存された状態として評価資料へ渡す。自律作業の発話配送は `run_id` と保存済みイベントの全文・起点cycle・宛先を照合する。自律作業の結果と能力要求を評価資料へ併記し、要求ID付きの通常の能力結果発話とは別の契約として検証する。配送のwireは [../api/event_stream.md](../api/event_stream.md) を正とする。

検証用DB、複製設定、証明書、画像、詳細ログは一時ディレクトリへ置き、通常終了時に削除する。`--keep-private` は原因調査に必要な場合だけ使い、調査と再検証の終了後に明示的に削除する。保存する結果から認証値を除き、会話、仮想時刻履歴、意味評価、状態の証拠、実時間の応答時間を残す。

各会話の直前に専用DBをsnapshotとして保存し、意味評価が通過したものは削除する。failやinconclusiveが残ったsnapshotは原因調査と同じ時刻での再検証に使う。`--cases-file` は `case_id / person / text / expected / cancel_all / virtual_time` を持つcase配列を受ける。開始時刻は最初のcaseのvirtual_timeとする。`--seed-data-dir` はそのcase直前の検証用snapshotディレクトリを指定する。画像sourceの有効状態もsnapshotと照合し、有効だったcaseには保存した `observation.jpg` を `--vision-image` で指定する。通常DBを再検証のseedに指定することは受理しない。再検証の `summary.json.profile=replay` は指定caseの結果であり、30日間の検証結果とは別に扱う。

## 代表ケースの割り当て

### 1年相当の検証

`scripts/run_virtual_time_conversation.py --profile one-year --image-manifest <manifest> --artifact-dir <result>` は隔離環境で1年分の経験を蓄積する。既定開始は `2026-10-04T09:00:00+09:00`。毎日の定期思考365回、週次と月次を含む会話400ターン以上、視覚の反復と変化、人物発話のない30日間、数か月後の予定、再起動を組み合わせる。10分間隔の全起床を再現する負荷試験ではない。

ネット画像manifestは `fixture_id / path / source_url / author / license / license_url / sha256 / visible_facts` を持つ非空配列とする。画像を直接確認した評価根拠と出典は評価側だけに保持し、アプリには画像を観測fixtureとして配送する。画像の撮影日を仮想世界の現在日時にしない。

直接確認済みの公開画像4枚は `scripts/prepare_virtual_time_images.py --output-dir <fixtures>` で取得する。出典・ライセンス・評価側の観測根拠は `scripts/virtual_time_image_sources.json` に保持する。取得した画像のhashが変わった場合は明示的に失敗し、新しい画像として直接確認する。

主モデル・送信前チェック・embedding・人格と活動設定を引き継ぐ。通常の設定DBはread-only接続のsnapshotから読む。設定済みELYTHのMCPとSkillも含め、外部操作は明示したローカル模擬サービスで結果まで確認する。模擬tool catalogは実サービスの現在schemaの確認とは別であり、実接続の可否は別に報告する。

各actionの完了後にDBと実行位置をcheckpointへ保存する。初日の画像観測、基本会話、共有許可、MCP操作も、それぞれを独立したactionとして扱う。途中のAPI失敗では完了した会話と記憶処理を保持し、中断したactionを直前checkpointから新しい専用プロセスで再検証する。`--resume-from <checkpoint>` は同じコード・docs・実設定・画像manifestの1年profileだけを受理する。コードを修正した場合、局所再検証の後に新しいDBで1年分を再実行する。実行中にコードまたはdocsが変わっても完走扱いにしない。

checkpointには評価器の校正結果とmock/実LLMの実行区分を保持する。再開時に実行区分を切り替えない。実LLMの完走は全件の意味評価がpassであることを必要とし、機械的mockの未評価結果を混ぜて合格にしない。

結果は `report.md / summary.json / transcript.md / evaluations.json / proofs.json / timeline.json / response-times.json / api-usage.json / provider-errors.json / world-results.json / itinerary.json` に保存する。API失敗は発生時にproviderの機械的なstatusと原因型を成果物へ記録し、別モデルへ切り替えない。呼出回数と提供されたtoken数を記録し、提供されないtoken数と費用は不明とする。実設定の資格情報はログへの書込み前と成果物の出力前に除去する。途中結果は全期間の合格として扱わない。未解決または中断時は再開用DBを専用private領域へ保持し、調査完了後に削除する。成功時はprivate領域を削除する。

評価に使う過去の発話は、初期事実・訂正・変化を持つ閉じたscenario IDと人物ごとの直近の完全な発話で選ぶ。評価に渡した根拠IDを保存する。LLM入力を文字数で切らない。初回の失敗、修正、再検証結果は別実行として保持し、正常化は全必須観点と最終コードでの1年完走を条件にする。

実LLMでの初回実行前に、評価器が既知の正答と誤答を区別することを確認し `evaluation-calibration.json` に残す。意味評価の fail / inconclusive、判断サイクルの失敗、記憶後処理や視覚整理の失敗はその場で停止して原因を調査する。人格の独立性、感情主体、人物の混同、共有範囲の許可と非公開情報、外部操作の観測・投稿・返信の実績を、返答と内部記録の両方で照合する。
記憶処理の完了待ちでは、後処理jobだけでなく選択中の記憶集合に属するtraceの `memory_trace.turn_consolidation_status` も検査する。返答が正しくても記憶統合が `failed` なら停止し、その会話前のsnapshotを原因調査用に保持する。

画像の校正では、全ての細部を列挙していない正確な説明と、画像に矛盾した説明の両方を評価する。評価用の観測根拠は主張の正確さを照合する資料とし、ユーザーが求めていない細部の省略だけで失敗にしない。
画像を使う意味評価には元画像も渡し、物の配置、内容、照明や影による色の見え方を直接照合する。評価資料の説明文や出典名から画像内容を補わない。添付画像は検証用の仮想外界であり、アプリの観測成功は内部traceで別に確認する。
照合資料の対象名も元画像の形状へ照合する。対象の全体と実際に写っている部分の説明を区別し、ある部分への正確な言及をほかの部材の不存在へ言い換えない。公園画像の天板と低い座面を備える構造物では、見え方に沿うピクニックテーブルの説明、ベンチ状の座面への部分的な言及、天板を否定する誤答を校正し、照合資料の旧表現や全体名の省略だけで正しい観測を否定しない。

想起候補と実際に採用された根拠も校正する。過去資料が RecallPack や workspace にあることだけでは誤採用と判定せず、最終の foreground 選択、抑制した候補、判断理由、返答を照合する。現在の説明へ過去資料を誤用した場合は失敗とする。
人物の対応表は評価者の資料であり、アプリへ渡った現在の参加者や想起根拠とは分けて照合する。同名人物への共有許可では、相手が曖昧な場合の確認と、既知の本人報告で相手を特定した限定許可を別のケースにする。許可条件の受け取り、共有先の同定、実際の開示を区別し、条件を受け取る返答だけで相手を同定済みと判定しない。別人へ開示する段階で同定と許可を照合する。
年間シナリオでは、曖昧な許可を受け取った後、本人が共有先を特定する前にBから仮題を尋ねるケースを置き、特定後の限定共有と両方を検証する。共有許可の意味境界は [../memory/想起と判断.md](../memory/想起と判断.md) を参照する。

設定に基づく活動の説明、今回の自己の判断、外部での実行実績も校正する。評価には有効な設定の `configured_activity_topics` と判断時に渡された同じviewを含め、設定を根拠とする限定が返答とepisodeで保持されているか照合する。設定を説明した返答に、過去の自己の関心の記憶だけを要求しない。設定の内容を確定した自己の習慣や実行済みの投稿へ強める例は区別して失敗とする。意味境界は [../runtime/定期思考トピック.md](../runtime/定期思考トピック.md) を参照する。

自己の受け止めの校正では、今回の見方や判断を答える正答、感情変化を確認できないまま現在の判断を答える正答、相手の発言を受け取るだけの不足した返答、記録のない過去の感情を作る誤答を照合する。現在の自己判断に感情ラベルや過去の感情記憶だけを要求しない。意味境界は [../runtime/判断と行動.md](../runtime/判断と行動.md) を参照する。

即時の能力実行の校正では、読み取りと単発の書き込み、その返却結果による確認・報告を含める。複数の外界作用や応答後にも残る履行責務を持つ依頼も照合する。意味境界は [../runtime/判断と行動.md](../runtime/判断と行動.md) を参照する。

人物ごとに共存する現在状態も校正し、Aの所在地を正しく答える例とBの所在地をAへ帰属させる例を区別する。評価には入力cycleの参照も渡し、状態の `source_ref` と一次発話の人物を対応付ける。内部状態は検証対象であり、本人の一次発話を上書きする正解資料にはしない。
活動の校正は、以前の本人報告による活動を正しく答えて現在の継続は未確認とする例、既知の活動を見落とす例、未観測の継続を確認済みとする例を区別する。状態保持と継続確認の意味は [../runtime/activity_state.md](../runtime/activity_state.md) を参照する。

設計済みの代表ケースは、次の基準で検証層へ割り当てる。

- 入出力が決定的で、LLM やサーバ起動が不要なものは fast test に置く
- 判断サイクル、scheduler、memory worker、event stream をまたぐものは mock smoke に置く
- 実 LLM の判断構造を確認するものは real LLM smoke に置く

自律判断 matrix、capability result follow-up、記憶品質、視覚観測は、当面 `scripts/run_long_smoke.py` を正とする。
fast test へ移すのは、仕様が固まった deterministic な境界に限定する。

返答時点の根拠と、その後の記憶処理の監査結果を分けて評価する。検証器は返答の配送後に記憶後処理まで待って trace を収集するため、今回の保存成功は返答時点の完了確認を意味しない。訂正の受け取りと保存完了の未確認を正しく伝える例、通常の記憶機能が存在しないと誤って説明する例を校正する。

現在の人物理解が維持されているかを尋ねる質問では、確認できる現在の内容と対象人物を照合する。過去の操作履歴全体の断言を追加の合格条件にしない。履歴や時系列そのものを求める質問では、その履歴を別に照合する。校正は、別人の訂正を混ぜず現在の好みを正しく答えて操作履歴の未確認を伝える正答、別人の好みを適用する誤答、確認できる現在の好みを見落とす誤答を区別する。

## 合否基準

fast test は pytest の exit code を合否にする。
mock smoke と real LLM smoke は exit code と `summary.json` の verified flag を合否にする。
LLM の自然文表現、完全な出力文面、偶発的な語彙選択を合否にしない。
