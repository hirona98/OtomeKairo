# 起動後の音声入力確認（2026-11-08）

## 確認した状態

今朝の起動後も、ERes2NetV2と11月7日に再登録した192次元の特徴量が読み込まれていた。
入力元、OSの録音ゲイン、モデルは前回と同じで、登録の消失は確認されなかった。

今朝の2発話は、話者一致度0.4430と0.5046で、保存済みしきい値0.3を通過していた。
STTも成功しており、結果コードは両方とも`wake_word_not_matched`だった。
保存済み音声起動ワードは「レイカ」で、AmiVoice側の指定プロファイルにも表記「レイカ」・読み「れいか」の辞書登録が存在した。

音声起動と会話受付期限の意味は[音声入力と話者識別](../../design/audio/音声入力と話者識別.md#音声起動ワード)を参照する。
起動直後の呼びかけ待ちに対し、文字起こしの先頭一致が成立していないことが今回の停止箇所である。
不一致発話の本文は保存しないため、実際にどのように文字起こしされたかを過去ログから断定することはできない。
利用者が発話の先頭に「レイカ」と付けたかは確認待ちである。

## 修正

従来、通常入力の呼びかけ待ちと会話受付中の両方が画面下部で「待機中」と表示され、失敗箇所を判別しにくかった。
以下を修正した。

- runtime stateに保存済み起動ワードを含め、画面ではそのワードを添えた呼びかけ待ちを表示する。
- 会話受付中と入力元の接続待ちを区別する。
- ダッシュボードに直近の起動ワード不一致を表示する。
- 起動ワードが空、または明示入力session中の場合は、無期限の会話受付状態を正しくsnapshotへ反映する。

wireの正本は[inspection](../../design/api/列挙とinspection.md)、表示規則は[WebUI通常画面規約](../../design/integration/WebUI通常画面規約.md)へ反映した。
起動ワードの一致規則、保存済み設定、話者登録は変更していない。

## 検証

- 起動時の待機、先頭一致、180秒の会話受付、起動ワード空配列の常時受付をテストした。
- 通常検証は1140件・304 subtestsが通過した（既存warning 1件）。
- JavaScript構文と`git diff --check`を確認した。
- 常駐サーバーへ反映後、モデル・入力元・登録が有効で、起動ワードを含む状態をAPIが返すことを確認した。

今回の本人判定は通過しており、話者の再登録を求める状態ではない。
呼びかけ済みでも不一致になる場合は、同じ入力条件で起動ワードの認識と先頭位置を追加確認する。
