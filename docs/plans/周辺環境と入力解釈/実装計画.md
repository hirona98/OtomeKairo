# 周辺環境と入力解釈の実装計画

## 状態と完了条件

未着手の実装計画である。[設計.md](設計.md) の案3を一つの完成形として実装する。
本計画の作成では production コード、運用設定、記憶 DB、接続中機器を変更しない。
既存仕様と同時に使う切替モード、案2の経由、旧契約の互換処理、DB マイグレーションは設けない。

完了条件は次とする。

- 元画像・センサー値を統合入力解釈と、許可された行動判断へ渡せる。
- 観測説明と変化判定が入力解釈の一回の生成から得られる。
- 会話、定期思考、API起床、画像の能力結果、自律 step が同じ観測型を使う。
- 取得失敗、期限切れ、比較 scope、記憶集合、媒体の保存境界が成立する。
- 既存の独立した画像説明生成を除去し、コードと現行正本文書を同時に更新する。
- fast test と必要な実 LLM 比較が完了し、未検証事項を完走扱いにしない。

## 実装順

以下は依存関係に沿った実装単位である。完了するまで旧経路と新経路を runtime で切り替える設定は追加しない。

### 1. 共通観測型と設定

- `src/otomekairo/observations/` に不変の snapshot、種別付き観測、取得状況、非永続の media bundle を置く。
- prompt 用 view と trace 用 view を明示した別メソッドにする。汎用の「全フィールドを JSON 化する」経路を作らない。
- sensor source、場所、画像の鮮度設定を config store の完全定義として追加する。
- camera source の場所参照、相互参照検証、設定変更時の runtime 無効化を実装する。
- sensor channel の最新値を持つ runtime と、snapshot を固定する lock 境界を実装する。
- 新規の観測 ID はコードで生成する。センサーの ID は source・channel・sample の組から固定 namespace の UUIDv5 で決定し、記憶集合を ID 生成へ混ぜない。

主な対象: `store/config.py`、`service/config/`、`defaults.py`、`world_state/models.py`。

### 2. 取得と API

- [API契約](API契約.md) の環境設定・センサー入力を HTTP routing と service に実装する。
- sensor input は runtime 更新だけを行い、自動の wake や意味判断を呼ばない。
- latest sample の同一性・本文・時刻を検証し、batch を原子的に適用する。
- capture の時刻を connector で取得し、結果 schema、受信検証、camera source metadata へつなぐ。
- 会話添付・wake reference は資料として media bundle に載せ、実際の撮影時刻との違いを保持する。
- 思考前観測では取得までを行い、取得ごとの画像説明・世界状態・活動状態の生成を除去する。

主な対象: `http_server.py`、`capabilities.py`、`service/input/wake_observation.py`、`service/input/wake_reference.py`、`service/spontaneous/capability_context.py`、camera connector。

物理センサー機種・通信方式が未選定でも、認証済みの模擬 producer で受信から判断まで検証できる構成にする。
vendor SDK、接続先資格情報、ドライバーの仕様は、実機選定後の connector 作業とする。

### 3. 入力解釈と媒体の転送

- `input_interpretation` の provider schema・validator・mock・repair に観測解釈を追加する。
- source と資料の view から text part と image part を対応付ける共通 message builder を実装する。
- `DecisionContext` と自律 step の文脈に当回の媒体参照を通す。永続化対象の dict には raw image を入れない。
- 独立した `generate_visual_observation_summary`、専用 prompt、専用 role 呼出を削除する。
- 人格の role 一覧、usage operation、mock fixture も新しい責務に揃える。
- 観測説明は原観測と参照で結び、数値・時刻・source metadata を生成結果から再構築しない。

主な対象: `llm/client.py`、`llm/prompts.py`、`llm/contexts.py`、`llm/schemas.py`、`llm/contracts.py`、`llm/mocks/`、`service/input/visual.py`。

### 4. パイプラインと自律入口

- 観測取得と統合入力解釈を、想起処理から独立した前段として切り出す。
- 解釈結果を値として引き回し、想起関数の内部で入力解釈を呼び直さない。
- query の構築を解釈後へ移し、当回の観測を直接利用する。
- 世界状態・活動状態の更新を、全対象の入力解釈後にまとめる。source ごとの根拠は保持する。
- world-state の単一型別 context を観測元ごとの `state_sources` と参照対応へ変更し、環境の統合キーを source / channel にする。
- 自律入口評価を更新後へ移し、既存の direct entry、定期思考トピック、API依頼の意味を維持する。
- 視覚専用の変化シグナルと候補生成を共通観測へ一般化し、センサーの意味上の変化も同じ入口比較へ通す。
- 見送り経路でも新しい観測を記録する。
- 通常 result follow-up と自律 run の正式な result 経路の両方で、画像を共通前段へ渡す。
- 環境・視覚の派生短期状態を `surroundings` へ投影し、同じ文を複数の prompt 欄へ複写しない。
- 隔離した自身の活動では、入力解釈・想起・判断の全段階で環境観測を空にする。
- 原観測、派生状態、取得状況を同じ source 参照で絞り、取得失敗後に古い world-state が現在値へ戻らないようにする。

主な対象: `service/input/cycle.py`、`pipeline.py`、`wake_pipeline.py`、`decision_comparison.py`、`world_state_source_pack.py`、`world_state_normalize.py`、`service/autonomous_run.py`、`service/spontaneous/`、`recall/`。

### 5. 保存、inspection、媒体解放

- 視覚記録を入力解釈後の観測確定で保存する。後続の cycle 保存から同じ視覚記録を二重生成しない。
- 視覚記録と sensor event を一つの観測保存取引にまとめ、cycle の終端未記録を行動完了と解釈しない。
- sensor sample は既存 event schema の新しい kind として保存し、記憶集合・観測 ID から event ID を安定させる。
- 同じ観測の後続 cycle は最初の event を参照する。clone では既存の event 参照書換えと記憶集合境界を維持する。
- 当回の新規観測を、同じ回の recall 検索で過去資料として再取得しないよう観測 ID で除外する。
- 失敗・見送り・正常終了の全経路で、観測の確定状態と media bundle の解放を保証する。
- current-state、cycle trace、cognitive-context に媒体を含まない観測参照と取得状態を出す。

主な対象: `store/cycle.py`、`store/visual.py`、`service/input/trace_build.py`、`trace_persist.py`、`trace_compact.py`、`service/config/inspection.py`、`store/clone.py`、`store/clone_visual.py`、`memory/`。

`events` の既存物理 schema を使い、センサー保存のためだけに telemetry 専用 DB を増やさない。
config schema の変更が必要な場合は現行の版検証を更新し、新規の隔離 DB で確認する。
既存版を暗黙に変換・削除しない。運用 DB の再作成やデータ廃棄はこの実装作業の範囲に含めない。
旧版 DB の起動を明示失敗とする既存方針と、運用適用時の手順を実装時に記載する。

## 検証

### fast test

既存の検証基盤に従い `.venv/bin/python -m pytest tests` を実行する。
意味判断の語彙一致や UI の DOM・文言を固定するテストは追加しない。

| 境界 | 必須確認 |
| --- | --- |
| 観測同一性 | 同一 sample の再送、同値の新規測定、source / channel 違い、再起動後 ID、別記憶集合 |
| 時刻 | 観測・受信の区別、未来時刻、遅延・期限切れ、逆転報告、反応時刻と監視開始 |
| 値 | 0、false、反応なし null、number / boolean の区別、非有限値、単位不一致 |
| 取得失敗 | 失敗報告後に過去値を現在値として出さない、新成功で回復 |
| snapshot | 取得中の更新と確定後の更新、source 設定変更、画像参照の件数・所有・欠落 |
| 生成契約 | 観測参照の完全対応、未知・重複・欠落、文字数、同じ snapshot での repair |
| 制御順序 | 解釈後に入口評価、見送り時の記録、想起時の入力解釈再実行なし |
| 比較 scope | 自身の活動へ画像・sensor・派生 recall が流入しない |
| 非同期 | 通常 result、自律 result、timer step、PTZ 後 capture、再起動後の媒体なし |
| 保存 | 視覚記録・sensor event の重複防止、当回 recall 除外、clone / delete、全終了経路の媒体解放 |
| API | 全件検証後の原子的適用、producer 照合、場所参照、版不一致 |
| 非保存境界 | raw image・base64・秘密値が DB、trace、run、request、job に入らない |

### mock smoke

隔離 DB と模擬 connector を使い、会話・定期思考・API依頼・通常能力結果・自律 step を通す。
画像なし、添付と camera の併存、複数 source、温湿度・人感、未取得、失敗、見送りを含める。
実運用の設定・記憶・接続先へ書き込まない。

### 実 LLM 比較

現行の案1相当の経路を、変更前の隔離 checkout で比較対象として固定する。
新実装に旧経路へ戻る runtime switch を作らない。
同じ原画像、測定値、人格、記憶、仮想時刻を使い、両実装を別 DB で実行する。

確認する意味ケース:

- 背景や小さな物体、容器の種類・中身など、画像の細部と不確実性。
- 画像に人物が見えず、人感の反応記録があるなど、異なる観測を併存させるケース。
- 別室の camera と温湿度計、場所未設定、古い反応、取得失敗を含むケース。
- 観測に関連する記憶の想起、当回の観測と過去の経験の区別。
- 定期思考の見送り、短い発話、定期思考トピックの独立した継続。
- 観測後の確認応答と、能力結果の非同期 chain の最終配送。

原画像・原測定値と最終結果を渡した LLM 評価を使い、未観測の断定、出所・人物・時刻・場所の誤りを確認する。
評価に失敗や inconclusive がある場合は合格にしない。
一部の画像で改善したことを全般の精度向上とは報告しない。
呼び出し数、入力・出力 token、各段階と全体の所要時間、provider が返した失敗を実測して残す。
費用は使用量と確認できる単価が揃う場合だけ算出する。
